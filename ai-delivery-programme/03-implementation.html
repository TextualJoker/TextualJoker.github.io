Stage zero

Before the first commit

The only part of this with a real deadline. All of it is settings, schemas or a page of writing — none of it is code, and none of it needs anyone persuaded of anything.

Eight things, none of which cost money
ItemWhat it isCost of not doing it now
Human review required A branch protection rule set when the repository is created, with exactly one bypass — the pipeline, on the lowest risk lane only. The highest-return control available, for one setting. Decide the low-lane bypass now rather than discovering in month two that two rules you both stated absolutely are incompatible.
Provenance on every commit A trailer recording whether AI authored the change, plus a check that it is present. Unrecoverable You cannot manage what you cannot attribute, and it cannot be backfilled.
The telemetry contract Three joins: deploys carry the commit, incidents carry the deploy, test results are stored per run against the commit. Unrecoverable Retrofitting this is the single biggest blocker in established organisations — an instrumentation programme wearing a quality programme's clothes.
Risk lane definitions Which surfaces are high risk here, applied automatically from the files a change touches. Risk becomes self-declared, and self-declared risk is always low.
The repository One repository, path-filtered CI from the first commit. The destination, not a migration. Path filtering added later means every change pays for every toolchain until someone fixes it.
Strictness settings Compiler strictness at its maximum, warnings treated as errors, escape hatches requiring a written justification. Unrecoverable in practice Nobody turns warnings-as-errors on against a year of existing code — the error count makes it a project, so it never happens.
Shared config, plus a parity check One place per language where every rule is expressed, and a job that fails when the two diverge. Projects extend; none redefine. Each project grows its own config, they drift, and adding a rule becomes eight pull requests and an argument.
The one-page practice standard How we prompt, what context we share, what we check before accepting output. In version control, with a named owner. Far cheaper to write while the team is small enough to agree. On a wiki it rots and is discovered to be fiction at the worst moment.

Six decisions that need a name against them

Distinct from the settings above — these have no artifact. They are about ownership and authority, and they get settled before the team grows past one conversation.

  • Who owns quality. Every engineer owns it; the quality function owns the capability to deliver it, never the execution. State it before the first quality hire, because that job description sets the precedent permanently.
  • The AI stance. What it may be used for, what review it needs, what data may go near it, who is accountable for accepting its output. Ambiguity is not neutral — people hedge, hide usage and over-rely, frequently all three.
  • What is non-negotiable. The short list nobody may switch off. Everything else is a default that can be argued with.
  • The boundary with legal and security. They own what must be true; engineering owns how that is satisfied and enforced. Settle it before the first tool is provisioned and it never becomes a dispute.
  • What "high risk" means here. Written once, applied automatically.
  • Where the standard lives. Version control, reviewed like code, named owner. Not a wiki page.
Non-negotiable

The four that cannot be added later

Everything else on this page can be introduced in month six at moderate cost. These four cannot — two in principle, and two in practice, which is a distinction worth keeping because the second pair is technically reversible and never actually reversed.

Why each one is a one-way door
ItemWhy it cannot be retrofitted
Provenance at commit History cannot be rewritten to add a fact nobody recorded. Every AI-specific measurement downstream depends on this existing — without it, "are AI-authored changes actually reviewed?" has no answer except a manual sample.
Test results stored per run A test run that was never recorded is gone. Results living only in CI console output on a 30-day retention looks fine for a quarter, and then flaky rate, feedback time and mutation score are permanently unobtainable.
Compiler strictness Technically reversible, practically not. Enabling it against a year of code produces thousands of errors at the worst possible moment, so in every organisation that defers it, it never happens.
Flag lifecycle rules An owner and a removal date required at flag creation. Introducing this against two hundred existing flags means auditing two hundred flags, which nobody will do — and the release model depends on flags staying manageable.

If only two survive contact with reality

Record provenance in the commit, and require human review on every change, from the first repository. Both are settings. Both are free today. Neither can be recovered cheaply once there is history — and every other AI-specific control depends on the first one existing.

Sequence

The five stages

Started by events rather than dates. Triggers are checkable — does a second team exist? has there been an incident? — so nobody has to litigate whether we are behind.

Stage 1

Decide and fund

Move on when: the first pipeline exists

Entirely conversation and contracts. Everything in section 01 above, plus the commercial groundwork: the model plan with per-user spend caps before any seat is issued, the data-processing agreement and retention settings, and legal confirmation on where staff may process what.

Also here: the salvage review, timeboxed to three to five days. Assess domain knowledge, integrations, application code and infrastructure separately — they have different answers. And brief the component library if an external firm is building it, because vendor lead times are measured in months.

Done when a repository created today inherits every one of these by default, with nobody remembering to apply them.

Stage 2

Paved road, and instrument as you go

Move on when: a second team appears, or the first incident

The minimum that makes every later step cheaper, and the point at which telemetry is emitted rather than excavated later.

  • Scaffold both halves of the codebase, strict, with boundaries enforced in each. This is the single most valuable hour in the plan — the strictness settings are what earn the language decision and they are effectively impossible to add later.
  • The shared CI workflow, called rather than copied, before the first workflow gets copy-pasted. After that it is archaeology.
  • The system overview — one page: what the services are, where data lives, which boundaries must not be crossed, what is deliberately undecided. The design stage reads this, so it exists before the first feature.
  • Design tokens and the generation chain, before any component, with the contrast check wired from the first commit.
  • The remaining shared homes, empty, each with an owner and a README saying what belongs in it.
  • Telemetry on, pointed anywhere, even a free tier. History cannot be generated retroactively.
  • Environments defined, with production carrying a required-reviewer rule from day one even while everything is manual.
  • The synthetic dataset started — long lead time, and without a convincing one people eventually reach for real data.

Done when every metric can be answered without asking a person.

Stage 3

One team runs the whole flow by hand

Move on when: the rough edges are logged

Resist expanding here. You want the setup refined against reality before anyone else inherits its rough edges.

  • Pick the pilot team by throughput, not enthusiasm. Engineers with a baseline of two or more changes a week retained the tooling at materially higher rates. Seniority and stated enthusiasm predicted adoption but not retention.
  • Ship the specification commands and run a real feature through the full lifecycle.
  • Wire the scenarios to run as tests. Half a day, and it is the load-bearing step — without it the specification is documentation and drifts within a month. Why that matters →
  • Generate the reuse catalogue and make the discovery stage blocking.
  • Size caps and test conventions in CI.
  • Accessibility enforced — lint rules, automated assertions, and the token contrast gate.
  • Error tracking, separately from metrics. They answer different questions and both are needed.
  • Approve-by-summarising, and watch time-to-approve alongside change size.
  • One command from a fresh clone to a running system. Write it while the pilot team still remembers what was undocumented.

Done when the pilot team would choose the paved road over going round it.

Stage 4

Expand and enforce

Move on when: about six months of incident history exists

Triggered by a second team, not by a date. Controls tighten because the risk profile changed, not because a quarter ended.

  • Onboard teams two and three socially. Let the pilot team do the persuading; make usage visible in review comments. Adoption spreads socially and mandates do not appear anywhere in the evidence.
  • Ship the blocking hooks — a small named set informed by what actually went wrong in the pilot, not what you predicted. Each mirrors a CI check rather than replacing one.
  • Report throughput and stability together, always. Merged changes and cycle time alongside change failure rate and two-week churn.
  • Name a spend owner and run the first monthly review. One person, one slide: total, per engineer, per merged change, and what moved.
Stage 5

The autonomous pipeline

Done when: headcount doubles and change failure rate doesn't move

Only start once the flow works manually. Automating a process you have not run by hand automates your misunderstanding of it.

  • Declare the bounds before writing any stage — iteration cap, budget cap, a success function the agent can evaluate itself, an escalation path, and no-progress detection. The budget cap is two numbers: per stage, and accumulated per run.
  • Build the shared stage harness first. If stages are written individually the bounds get implemented eleven times and eleven ways, and the one that gets skipped is the one that runs away.
  • Wire triage first — the output is a comment, so it is fully reversible and the safest place to learn how headless agents behave.
  • Then the rest, in reversibility order, each shadowed first and promoted only after a fortnight of being right. Reuse, then design and decomposition, then verification, then implementation, then staging, and production last.
  • Build the reversibility stack before automating deployment. If automated reversal cannot be achieved, deployment stays a human gate — that is a legitimate outcome, it just needs deciding rather than discovering.
  • The golden set — 15 to 20 recorded past requests with known-good outcomes, run nightly. Once agents run delivery, a prompt change is a production change.
  • Register the pipeline as a non-human identity — least privilege, credential rotation, audit logging. It is a service account with production access.
The ordering mistake to avoid

Every one of these stages is tempting to start early, and stage 5 is the most tempting of all because it is the interesting one. Automating a workflow nobody has run manually produces a fast, confident version of the wrong process — and because it is automated, the wrongness is now consistent and hard to see.

The four steps that carry the most weight

17 — strictness settings. Effectively impossible later, and it is what earns the whole compiler argument.

15 and 16 — provenance and the telemetry joins. Free today, unrecoverable tomorrow, and everything measurable downstream depends on them.

28 — scenarios running as tests. Half a day, and every claim this plan makes about specifications not drifting rests on it.

If a quarter goes badly and only four things got done, those four leave you in a recoverable position. Nothing else on this list is unrecoverable.

On the four steps marked new

Steps 42, 43, 44 and 45 were not in the original plan. They came from reading an existing agentic workflow already running elsewhere in the business, which solves all four and which this design had simply not considered — run ownership with an explicit close, a path for ambiguous requests, scope bounded to the approved plan, and a decision point for whether durable documentation needs updating.

Worth saying plainly: that workflow is ahead of this plan on all four. Taking them is not a compromise, it is the obvious move.

The test before adding a twenty-sixth

Does complying with this cost an engineer anything? If not, mandate it today and never discuss it again — that is a control. If it does, it is a practice, and practices are earned rather than announced.

And the second test: does it prevent a defect class or shorten a feedback loop? If neither, it is ceremony. Remove it rather than refining it.

The testing contract

What proves what

The most common question a new engineer or an agent asks, and the one most codebases never answer — so everything drifts to end-to-end.

Build this, prove it this way
You're buildingDefault proofBudgetAlso required
A pure function or formatterUnit, in memory< 10msNothing. If it needs more than this, it is not pure — move it.
A domain ruleUnit, valid and invalid cases both< 10msEvery rule ships with at least one rejection test.
A boundary validatorUnit, valid and invalid both< 10msA validator nobody tested against bad input is decoration.
A UI componentIn-memory render, queried by role< 100msAn accessibility assertion on anything interactive.
An API endpointIntegration, against a real database in a container< 2sAn authorisation test for every endpoint touching member data. No exceptions — this is the row that catches the most common serious finding in AI-written code.
A cross-service callContract test — consumer records, provider verifies< 1sBreaking-change detection on the published schema.
A database migrationUp and down against a restored snapshot< 30sProof the previous version still starts against the new schema.
A user journeyEnd to end, driving the approved scenario< 30sOne per acceptance scenario. Not one per component, not one per route.
Anything on a sensitive pathAll of the above, plus mutation testingNightlyCoverage means nothing without it, and generated tests inflate coverage while asserting little. Score the changed lines, not just the codebase — the question is whether this change is pinned, and a healthy overall score hides a new path nothing asserts.

A test may only sit at a higher layer if it cannot be written at a lower one

The reviewer's question is never "is this tested?" but "is this tested here, and why not lower?"

The suite has a hard budget: ten minutes end to end. When it exceeds that, the fix is moving tests down the pyramid or running only what a change affects — never deleting coverage, and never accepting a slower loop.

The collision to plan for now, not later

Every acceptance scenario needs an end-to-end test, and none can move down the pyramid — being end to end is what makes it the contract. At roughly thirty seconds each, ten minutes of serial execution is about twenty scenarios, which a team shipping two or three a feature reaches within months.

Resolve it in advance: shard across CI workers, run only the scenarios a change touches on a pull request, run everything on merge and nightly. The ten minutes is a promise about the pull-request loop, not a cap on how many scenarios may exist — say it that way, because said the other way it eventually becomes an argument for having fewer acceptance tests.

Enforcement

Where a rule can live

Four places, ordered by how binding each is. Choosing the wrong one is the difference between a standard that holds and one described in an onboarding session and then forgotten.

Ordered by bindingness
MechanismUse it forWeakness
A CI checkAnything objectively decidable. The default — if a rule can live here, it lives here.Feedback arrives minutes after the mistake rather than at the moment of it.
A hookThings that must never happen at all: real data entering the repository, tests edited to make them pass, pushing straight to the main branch.Local only. Every hook mirrors a CI check, never replaces one — a hook alone is bypassable.
A loaded skillThings requiring judgement applied consistently: which test type to write, how to structure a component, what the tooling is bad at here.Advisory. It shapes what gets produced; it cannot guarantee it.
An instruction fileAlmost nothing. Only what is true of every task in the repository, in a few lines.Costs tokens every session, and adherence falls as it grows — a long file causes rules inside it to be ignored.

Move rules down this list, not up

The instinct when a standard is missed is to write it down more prominently. That is moving up — toward prose, toward advisory, toward decay. The fix is always the opposite: can this be a skill, so the agent applies it by default? Can it be a CI check, so it is decided rather than debated?

This also resolves the tension between context budget and standards. Every rule moved out of prose and into a check costs zero tokens and becomes binding — so shrinking the instruction file strengthens enforcement rather than weakening it.

Why skills matter more than they look

A CI check catches a mistake after it is made. A skill means the mistake is less likely to be made at all. They are the same standard expressed twice, deliberately — the skill makes the right thing the default output, the check makes the wrong thing impossible to merge. Skills without checks decay silently; checks without skills produce a loop where the agent generates, fails and retries.

The review queue collapses Pickup time rising. Change size distribution widening. Work in progress climbing while merges stay flat. Tighten the size cap before adding reviewers. Move more baseline checks off human eyes. Do not add parallelism — it multiplies input to the constraint.
Quality erodes invisibly Two-week churn rising. Duplication rising. Revert rate up while throughput looks excellent. This is the documented default trajectory, not bad luck. Raise the lane of whatever is churning, and check whether reviewers are approving without reading — a pre-reviewed change makes rubber-stamping easy.
People route around the tooling Hook overrides appearing frequently. Hooks disabled locally. Usage dropping among strong engineers specifically. You have built a cage. Remove hooks rather than adding them, and find out what was blocked that should not have been. Losing visibility is worse than the risk you were guarding.
Review becomes approval Approvals landing within two minutes of a change opening. No comments on non-trivial changes. Nobody announces that reviews have stopped being real. A blind audit twice a year — twenty changes, two judges, four criteria — answers it in half a day.
The specification gate turns ceremonial Scenarios written in technical language. Product approving within minutes and never asking for changes. The gate is already dead. Fix the language, not the process — if product cannot evaluate it, they are not reviewing it, and you have lost the cheapest quality intervention available.
An irreversible data change ships A migration without a contract-phase label. Destructive operations outside a contract release. Rollback drills failing at the database step. The most dangerous failure here, because it silently voids the whole reversibility argument. The canary reports healthy — nothing was reading the dropped column yet — and rollback then cannot start the previous version. Rehearse a rollback against a restored snapshot quarterly; a rollback path nobody has run is a hypothesis.
Flags accumulate Flags past their removal date. Nobody able to say which combinations are live. The cleanup rule was advisory rather than a build failure. Make it fail, and separate temporary release flags from permanent operational switches — mixing them is how the rule gets abandoned.
An unattended path fails silentlyA scheduled job that emits nothing when healthy and nothing when dead. Ingestion counts falling without an error. Quarantine volume at zero for a suspiciously long time.The failure that hides longest. A screen that breaks is reported in minutes; a nightly job that exits early is reported never. Unattended work must emit a signal on success, with an alert on the absence of that signal — and it takes a higher lane than the same logic behind a screen, because nothing else will catch it.
Nobody can explain what is automated Disagreement about whether a lane is gated. Autonomy levels not written down anywhere current. Publish the levels with a named owner per lane. A silent demotion after an incident is how this erodes — make every change visible, with a stated reason and a route back.
The signal that matters more than the others

Escaped defects climbing as headcount grows, while every control reports green. The controls are measuring the wrong thing. Say so publicly rather than quietly adding another one — and note this is precisely the case the telemetry contract exists to make visible early rather than late.

Deliberately excluded

What not to build yet

Each of these is defensible later and wrong now. Naming them stops them being rediscovered as good ideas every quarter.

Defer until the pain is real
ThingWait until
Parallel agent sessions per developerReview throughput demonstrably has headroom. Running several sessions each multiplies input to the constraint — this is the clearest "do not" in the whole plan.
Centrally managed device policyThere is an endpoint estate, or a compliance requirement forces it. Below that it is overhead that reads as distrust.
Role-based agent teamsNever, for coding. Optimises 0.5% of observed failures at roughly 15× the token cost.
A separate review lane for AI-written codeNever. Authorship is not detectable or attestable, so it is enforced by honesty and penalises it — and within a year everything is agent-assisted anyway.
Specification ceremony on low-risk changesNever. That is the entire point of lanes.
Paid observabilityFree tiers cover a team this size comfortably.
A release confidence scoreEverything it would synthesise is real and trusted. Built early it produces a number nobody believes — and then the gate comes back wearing a dashboard.
Self-hosted modelsSpend is stable enough to forecast against a modelled workload. Keep the three interfaces abstract and the option stays cheap.
A spec dependency graphNever, if specs are sized per change. The graph problem is an artefact of durable area-specs. Size them right and it does not arise.

If only three things get done

One owning team per module. Free now, near-impossible to retrofit socially.

The shared CI workflow, before the first copy-paste. The moment one gets pasted, drift begins and never stops.

Cost controls before the first seat. The best-documented failure in this space is an organisation that measured a real productivity gain and cancelled anyway.
