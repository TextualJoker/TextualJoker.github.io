Forty-eight repositories is not a migration project

The instinct on hearing "we want one repository" and "there are forty-eight" is to plan a consolidation. Don't. Create the monorepo as the home for what you are building, and let the old repositories die as their code is replaced or retired.

Most of them are infrastructure and will not move at all — infrastructure-as-code belongs with the thing it provisions, and there is no agent-context argument for dragging it in. Of the application repositories, the ones being rebuilt never migrate; they are superseded. The ones being kept move when someone next has a reason to touch them.

Migration by attrition costs nearly nothing and delivers the benefit — whole-system visibility for agents — from the first day the new repository exists. A consolidation project delivers the same benefit six months later, having consumed the six months.

The number worth getting

How many repositories hold application code, and how many of those are candidates to keep after the salvage review. That is the figure that matters, and it is almost certainly single digits. Forty-eight is a scary number that mostly describes Terraform.

Question 01

Deploying continuously without releasing continuously

Q

Clinicians shouldn't see the product change under them. Does that break the pipeline?

Short answer

No — and this is the single strongest argument for feature flags there is. Deploy continuously, release on whatever cadence product wants. They are different events and conflating them is the actual problem.

Three things get called "shipping" and only one of them is visible to a clinician:

Three events, three owners
EventWhat happensWho decidesCadence
DeployCode reaches production infrastructure. Nobody sees anything.The pipelineContinuous
ReleaseA capability becomes visible to users. A flag flips.ProductWhatever suits clinicians
RollbackEither one is reversed. Deploy reverts automatically on a health signal; release reverts by flipping the flag back.Automatic, or one personSeconds

So the constraint as stated — full CI/CD to staging, batched dot releases beyond that — is satisfiable without giving up anything the pipeline depends on. Code flows to production continuously, dark. On release day a set of flags flips and clinicians see one coherent change.

The version of this that fails

Batching the deploy rather than the release. If code sits on a branch for three weeks waiting for a release window, you lose small batches — and small batches is the assumption every other control in this plan rests on. Review gets harder, the diff gets bigger, and when something breaks you have three weeks of changes to search rather than one.

Say it precisely when you challenge the constraint: nobody is proposing that clinicians see daily changes. The proposal is that code reaches production daily and clinicians see changes monthly. Those are compatible, and the second is a product decision nobody in engineering needs to win.

Where your instinct to challenge is right, and how far to push

Some changes genuinely should go straight out: a copy fix, a logging change, a bug fix restoring intended behaviour. That is Lane 1 in the risk model, and "the user sees a defect corrected" is not a confusing change. Worth winning, but you don't need it. The flag model gives you the engineering benefits regardless, so this is an optimisation rather than a dependency — which is a much easier argument to have.

Where a flag actually lives

“Put it behind a flag” is the answer people give and it is not specific enough to build from. A flag has three parts, they live in three different places, and collapsing them is what makes the whole idea sound vague.

Three parts, three homes
PartWhat it isWhere it livesChanged by
Definition Name, description, owner, removal date, default state, release group. In the repository, version controlled. A pull request — so it is reviewed like anything else.
Evaluation The code asking whether this is on for this context. Application code, through one interface rather than scattered checks. A pull request.
State The actual on/off value, per environment. A flag provider, outside the repository. A toggle. No deploy, no build, no merge.

The third row is the whole point

State cannot live in the repository. If flipping a flag requires a deploy then you have gained nothing over deploying the feature itself — and the entire argument for separating deploy from release collapses.

Which provider, who may flip one, and what a flag targets are all still open — set out below.

How a dot release actually happens

  1. Staff exposure first. The group is switched on for internal users while clinicians still see nothing — this is the step that buys back the risk of code sitting dark.
  2. Product flips the group on release day. One action, one coherent change, and the cadence is genuinely their decision.
  3. A cleanup change removes the flags and the dead branches after a bake period.

How the flip actually reaches a clinician

The cost of this, stated plainly

Code sitting dark for six weeks is code that has never run in production. “We deploy continuously” is doing less work than it sounds if nothing is exercising the new path — you have moved the risk rather than removed it.

Step 3 above is what buys it back. Internal users on the new path for a week before the group release gives you real production exercise, real data shapes and real error rates, with nobody clinical affected. Skip that step and the first genuine test of six weeks of work is the release itself, which is the situation this whole design exists to avoid.

On testing combinations, which sounds worse than it is

Every flag is theoretically a branch, so n flags is 2n states. In practice you test two: everything currently released, which is production, and everything in the next group, which is staging. That is only true because release flags flip as a group rather than individually — which is a second reason to group them, beyond giving clinicians a coherent change.

Flag hygiene, which is not optional

Every flag is a branch in the code and a multiplier on the test matrix. Left alone they accumulate until nobody knows which combinations are live. So flags get a lifecycle from day one:

  • Every flag has a named owner and a removal date at creation. Both required fields, not conventions.
  • CI fails on a release flag past its removal date. Not a warning — a failure, or it will be ignored.
  • Kill switches are marked as a different kind so the cleanup rule skips them rather than being abandoned because it kept flagging things that should stay.

Cheap now, and genuinely painful to introduce against two hundred existing flags.

Question 02

Claude now, possibly our own models later

Q

Does a future move to self-hosted models change the plan?

Short answer

It changes the economics, not the architecture — provided three things stay abstracted from day one. None of them costs anything to do now and all three are expensive to retrofit.

Keep these portable and the switch stays a configuration change
Keep abstractWhat that means concretelyIf you don't
Where the model is calledOne place in the codebase makes model calls. Everything else asks that place. The pipeline harness already takes the model as an input rather than hard-coding it.Model-specific calls scattered through the code, and the switch becomes a refactor across every service.
What is sentPrompts, skills and agent definitions are files in version control, not strings in code. They already are, for other reasons.Nothing to port. You rewrite them from memory.
How you know it still worksThe eval set — recorded past work with known-good outcomes. This is the portability test.The switch becomes a matter of opinion, and it will be argued rather than measured.

What genuinely would change

  • Two commercial features disappear. The batch discount on non-urgent work, and the built-in budget ceiling used to bound agent loops. The budget one matters more — it would need rebuilding in the harness.
  • Prompt caching behaves differently, and caching is the largest single lever on spend. The cost model needs rebuilding, not adjusting.
  • The compliance position changes shape entirely — self-hosting removes the third-party processing question and replaces it with an infrastructure security question. Different, not simpler.
The honest caution

Self-hosting is rarely cheaper than it looks at this size. It converts a monthly bill into capital plus a fraction of a person, and that person is a permanent commitment rather than a one-off. It is the same shape as the on-premise argument: frequently right for predictable, high load, and almost never right if you forget to count the person.

The decision needs a modelled workload rather than a comparison of headline token prices. Worth revisiting when usage is stable enough to forecast — which is roughly the point the spend review has six months of data.

Question 03

What a spec is actually authoritative for

The hardest question in the feedback, and the one where getting the framing right resolves most of the rest.

Q

Specs live in the repo and describe intent. But are they the source of truth for how the system behaves?

Where the spec lives, and where the scenarios live

The decision

The issue is the spec. It is written and revised there while the work is live, product approves it there, and at merge it is snapshotted into the repository as a frozen record.

The scenarios live with the feature they test, not with the change that introduced them — tagged so each one still traces back to its issue.

Those two halves are organised on opposite principles, and that is the point rather than an inconsistency.

Two artifacts, two organising principles
The specThe scenarios
Organised byThe changeThe feature
BecauseIt records intent at a moment. It is a historical document and you find it by asking why is this like this.They describe behaviour as it is now. You find them by asking what does this screen do.
Lives atACME-412, snapshotted to specs/ACME-412.mdfeatures/discharge-intake.feature
After mergeFrozen. Never edited, so it cannot drift.Living. Later changes add, alter and remove scenarios in place.
The mistake this avoids — and it is an easy one to make

The obvious move is to put a change’s scenarios next to its spec, in a folder named after the change. Do that and two hundred changes later you have two hundred feature files, three of which touch the discharge screen, and no way to know what is covered without reading old issues.

A change does not create a feature file. It adds scenarios to the one that already exists. Open that file and you see everything the capability does today, in one read.

features/discharge-intake.feature 
Feature: Discharge intake

  @ACME-100-R1
  Scenario: Valid discharge creates a care plan draft
    ...

  @ACME-412-R2
  Scenario: Unparseable summary is queued for review
    Given a discharge message with a malformed summary
    When  intake processes it
    Then  the record is queued for manual review
    And   no care plan draft is created

The tag is the whole traceability mechanism. What does this system do? Read the feature file — always current, organised by capability. Why does it do that? Follow the tag to the issue, and to the frozen snapshot of what was agreed when it merged.

Why the snapshot, when the issue already exists

One generated file, never hand-edited

At merge, CI copies the issue body to specs/ACME-412.md and commits it once. It is generated output, like the API client — read-only, and hand-editing it fails the build.

Two things that buys. The record travels with the code: check out any commit and the requirement that produced it is there, which is the question a health-plan security review actually asks. And it cannot be rewritten after the fact — an issue edited a year later leaves no diff anyone will read, while a committed snapshot is fixed at the moment it mattered.

No dual maintenance, because nobody maintains it. It is taken once and never touched.

The mechanism that makes part of the spec undriftable

Split the spec by whether a machine can check it.

Three layers, three different lifespans

The rule that follows: anything that must not drift, make executable

Everything else is context, and context ages. That is not a failure — a decision record is supposed to describe the past.

The failure mode to design against is a spec that reads authoritative and is checked by nothing. It is worse than no spec, because people trust it. If a statement in a spec matters enough that being wrong about it would hurt, it belongs in the executable layer or it belongs in a test.

Why this also answers the product-sign-off question

The scenarios product approves are, literally and without translation, the tests that gate production. There is no step where someone converts an approved scenario into a test and introduces a gap. That single wiring decision is what makes the whole spec chain trustworthy rather than ceremonial — and it is a half-day of work, once.

The identifier that makes all of this work

Freezing a spec at merge only works if you can find it again eighteen months later. That needs one stable identifier, created once and carried everywhere — and the tracker already issues one.

One key, carried through every artifact

The one discipline this depends on

The spec is updated freely while the work is in flight, and frozen the moment it merges. That distinction is the whole mechanism.

Updating during the work is correct — the interview surfaces things and the document should follow. Updating after merge is how you rebuild the drift problem: when a later change alters that behaviour nobody goes back to amend the old record, so it becomes quietly wrong while still reading as current. A frozen record cannot be wrong; it can only be historical, which is what it is meant to be.

What this looks like when behaviour has changed three times

A capability added in one change, modified in a second, given an edge case in a third, produces three frozen specs. To know what it does now, read the tests. To know why it is like that, read the three specs in order — which is a changelog, and an honest one.

Compare that with a single maintained document claiming to describe current intent, which is wrong from the second change onward and gives no indication that it is. Three accurate historical records beat one confident inaccurate one, and they cost nothing to keep because nobody maintains them.

If work is tracked somewhere other than the repository host

Put the tracker where the pipeline can read and write it without glue — the repository host, since the repositories exist there regardless. If the wider business runs portfolio reporting elsewhere, mirror one way only, from that system into this one, so there is still a single writer per fact. Two systems both editing the same field is the reconciliation problem this design avoids everywhere else.

Question 04

How big is a spec, and how do specs know about each other?

Q

One spec per domain, service, feature, or bounded context? And how do you manage the dependencies between them?

Short answer

One spec per change. Not per domain, service, feature or bounded context — per change.

And the dependency-graph problem you haven't seen solved is mostly an artefact of getting that wrong. Fix the granularity and it largely stops existing.

The reason the graph problem is hard is that people write specs as durable descriptions of an area. A durable spec has to be maintained, has to know about its neighbours, and has to be reconciled when two changes touch it — which is exactly when you start wanting a dependency graph, and exactly when nobody has time to maintain one.

A spec that describes one change never has that problem. It is written, approved, implemented, merged — and then it is history. It is never updated, so it cannot drift and it cannot conflict. Its scenarios are added to the feature file for the capability they describe, and live on there as tests. The document becomes a record of why something was built.

The two models, and what each costs
Spec per area (domain / service / context)Spec per change
LifespanForever. Must be maintained.Until merge. Then it is a record.
Can it drift?Yes, immediately and permanently.No. Nothing to drift from.
DependenciesReal, growing, and needing a graph nobody maintains.Largely absent — two changes rarely depend on each other's intent.
Merge conflictsTwo changes to one area edit one document.Two documents, no conflict.
"What does this area do now?"Read the spec — and it may be lying.Read the tests. They cannot lie.

So where does durable truth live?

The instinct behind "one spec per domain" is sound — something should describe the whole. It just isn't a spec. Three artifacts do that job, each with exactly one responsibility:

What replaces the durable spec
ArtifactAnswersKept true by
The test suiteWhat does the system do now?It runs. Nothing else is required.
Architecture records
ADRs plus a one-page overview		Why is it shaped this way, and what are the pieces?Small, rarely changes, superseded rather than edited. See section 07.
The contracts
API schema, event schemas		What are the interfaces?Generated from the code, so true by construction. CI fails when the generated copy is stale.

If you want a spec to be durable, you actually want one of those three

That substitution is the whole answer to the graph question. You are not maintaining a web of interdependent living specifications. You have a chronological record of changes, a test suite that is the current behaviour, and a small architecture record that explains the shape.

Nothing in that set needs a dependency graph, because nothing in it needs reconciling with anything else.

The dependencies that are real

Two genuine cases remain, and neither needs a graph:

  • Two changes touching the same code. That is a merge concern and version control already solves it. It is not a specification problem wearing a disguise.
  • A change breaking an interface something else depends on. Solved by contract tests and automated breaking-change detection on the published schema — the machine tells you, at the moment you do it, without anyone having drawn a diagram.

The one graph worth having is the trace from a requirement to its tests to the code that satisfies it, and that is a query over identifiers rather than a maintained artifact. The requirement ID appears in the spec, as a tag on the scenario that proves it, and in the commit message — so the trace is a search, generated on demand and never stale.

Why nobody has shown you a working spec-dependency graph

Because the ones being built are solving a self-inflicted problem. A maintained graph of living specifications has all the properties of a second codebase — it needs writing, reviewing, refactoring and testing — with none of the tooling. The teams that appear to have solved spec drift have mostly stopped asking documents to be authoritative, which looks like a smaller idea than a graph and works considerably better.

Question 05

How work gets chunked

Q

What is the unit of work? A feature, a product ask, something smaller? When is it too big or too small?

Short answer

Two different units, and conflating them is the trap. The unit of intent is sized by user value and stays whatever product already uses. The unit of change is sized by what one person can review — and that number is fixed, not negotiated.

Two units, two sizing rules
Unit of intentUnit of change
IsA feature. Your existing format works unchanged.One reviewable pull request.
Sized byUser value. Product owns this.Reviewability. Engineering owns this and it is not a judgement call.
Who splits itProduct, as now.The pipeline, automatically, at the decomposition stage.
Test for "too big"More than one outcome, or needs more than one spec.Over the diff cap. Roughly 400 lines.
Test for "too small"Not worth a specification conversation.Nothing is too small. Small changes are free.

Your existing feature format feeds this directly. Features with requirements in scenario form are the input — that is the same format the specification stage produces, so nothing about how product expresses intent has to change. What changes is what happens next: the breakdown into tasks is mechanical and the pipeline does it.

The one sizing test worth memorising

Can one person read this change and say what it does, without opening a second tab?

If no, it is too big — split it. That test is better than a line count because it catches the change that is four hundred lines across eleven files and genuinely incoherent, which a cap alone waves through.

The cap is the mechanical backstop; this is the judgement it approximates. Agent-opened changes already wait over five times longer to be picked up for review, and size is the main driver. Every line above what a person can hold in their head is a line that makes the queue worse.

Where "too small" does bite

Not in the size of the change — in the process applied to it. A specification conversation for a copy fix is pure ceremony, and a team made to do it will route around the whole system within a month.

That is what the risk lanes are for. A copy change gets automated checks and ships. A change touching member data gets a written spec, two reviewers and a named approver. Same pipeline, four different depths — and the depth is set by which files were touched, not by anyone's estimate.

Question 06

Where the system architecture lives

Q

Decision records cover individual decisions. Where does the overall architecture live, and how does it get seeded from nothing?

Short answer

Three artifacts, three jobs. The mistake is trying to make one document do all three — that is how architecture documents become long, wrong and unread.

The architecture record, split by what keeps each one honest
ArtifactAnswersWritten byChanges
Decision records Why is it like this? A person, one decision each Never. Immutable once accepted; a new decision supersedes rather than edits. The history is the point.
The system overview
one page, hand-written		 What is there, what talks to what, where does data live, where are the boundaries? A person, reviewed like code Rarely. If it changes monthly it is too detailed.
Generated views What does it look like right now? Nobody — generated Every build. Dependency graph, interface surface, the catalogue of what exists.

If it can be generated, generate it

The hand-written part is only what a machine cannot derive: intent, boundaries, and why. Everything else — which service calls which, what the interfaces are, what already exists — is read out of the code on every build and is therefore never wrong.

That is what keeps the written half short enough to stay true. A hand-drawn dependency diagram is wrong within a fortnight and is then actively misleading, because people trust diagrams more than prose.

Seeding it from nothing

The overview needs to exist before the first feature, because the design stage reads it — an agent planning a change needs to know what the pieces are. Starting from nothing, it is about an hour:

  • The services and what each is for. One line each. At the start there may be three.
  • Where data lives, and which store is authoritative for what. This is the row people skip and regret.
  • The boundaries that must not be crossed — which layer may reference which. These become enforced rules rather than intentions, so writing them down has teeth immediately.
  • External systems and what we depend on them for.
  • What is deliberately not decided yet, so an agent proposes rather than assumes.

Keep it to a page. It grows as the system does, and the discipline that keeps it useful is that anything a generator could produce gets deleted from it.

This is also the answer to your eFax example

"We need to send a fax" is not a specification question and it does not belong in a feature. It is a system-level decision: buy or build, which provider, what happens on failure, does it need an audit trail, where does it sit relative to everything else.

That is a decision record, and it is written before any feature depends on it. Section 08 is about who does that work — it is the part of analysis that survives, and it is the more interesting half.

Question 07

What a team is for, once the pipeline does the breakdown

The sharpest question in the feedback. It is asking whether this design leaves anything for a team to do together.

Q

If the pipeline decomposes the work, do we still need an analysis phase? Is there collective work left, or is it individuals writing specs with product?

Short answer

The analysis phase doesn't disappear. It loses its clerical half and keeps its design half — and the half it keeps is the one that was always underserved.

Analysis has historically bundled two very different activities:

What happens to each half
ActivityWhat it wasNow
Translating a requirement into tasks Reading a feature, working out which components change, writing task cards, estimating each. Automated This is mechanical, and it is exactly what the decomposition stage does — faster, more consistently, and with every task traced back to a requirement.
Deciding how the system should work Squeezed into the gaps, usually by whoever was most senior, often after implementation had started. Expanded This is now the team's primary collective work, and it happens before anything enters the pipeline.

What a team does together

Four things, all of which need more than one person and none of which a pipeline touches:

  • System-level design. Your fax example, exactly. Buy or build, which provider, failure behaviour, where it sits. These are the problems that need someone to think, and they produce decision records rather than tickets. This is what the smart people you hire will spend their time on.
  • Risk classification for this product. Which surfaces are genuinely dangerous here — what counts as clinical logic, what touches member data, where a mistake is unrecoverable. That is domain judgement, it is specific to Medicare aftercare, and it gets written down once and applied automatically forever after.
  • What the tooling is bad at, in this codebase. The patterns AI reliably gets wrong here — the module whose conventions it always violates, the library version it consistently misuses. Every engineer discovers this privately within weeks and none of them share it. Written down, it becomes something the agent loads before generating, so it stops happening.
  • Boundaries. Where one service ends and another begins; what belongs in the domain model. Wrong boundaries are the most expensive thing to fix later and the least suited to being decided by one person quickly.

The rhythm changes shape rather than disappearing

Instead of a planning ceremony that mostly produces task cards, you get a recurring architecture forum where the fax-shaped problems get decided and become records — and a retrospective that updates what the tooling is bad at.

Both are genuinely collective, both produce artifacts the pipeline consumes, and both are more interesting than estimating cards. Specification work with product is individual, and that is fine — it always was, we just used to do it in a room with eight people watching.

On hiring, which is the sharper end of the question

This is more attractive to strong engineers, not less. You are removing the clerical half of the job and keeping the design half. An engineer who wanted to spend their week deciding how the system should handle a failed fax delivery now spends their week doing that.

The people who won't like it are those whose value sat in the translation layer — turning requirements into tasks. That is a real hiring consideration and worth being honest about in interviews rather than discovering in month three. The role you are describing is closer to a systems designer than a ticket implementer, and saying so attracts the right people and filters the wrong ones.

One thing not to lose

The pipeline decomposes work well and it cannot tell you the requirement was wrong. That is what the specification gate is for, and it is why the person writing the spec with product should usually be an engineer rather than a business analyst — the value is in the questions asked during the interview, and those come from knowing what the system can and cannot do.

The operating model

What persists, who does what, and how a week actually runs

The pipeline describes how one change flows. This describes how a company organises around it — which is a different question, and the one underneath several of the others.

What is durable and what is disposable

Most of the confusion about specs, architecture and documentation dissolves once you separate artifacts by lifespan rather than by subject. Three categories, and almost every artifact belongs to exactly one:

The mistake this prevents

Nearly every documentation problem in an engineering organisation is an artifact in the wrong row. A transient document treated as durable becomes a lie that people still trust. So the test for any new artifact is a single question: how long is this meant to be true for? The answer decides where it lives and who is responsible for it.

The specification interview belongs to an engineer

Not to an analyst, and this is worth being deliberate about. The value of that conversation is in the questions asked — what happens when the feed is late, what should explicitly not happen, does this need to survive a restart — and those come from knowing what the system can and cannot do.

What is deliberately absent

No sprint planning, no estimation ritual, no stand-up whose purpose is status. Status is visible in the pipeline — every change has a state, a lane and a stage, and reading it is faster than asking. A daily meeting to recite what a dashboard already says is the ceremony this design exists to remove.

Keep a short daily contact if the team wants one, but let it be for blockers and offers of help, not for reporting.

How concurrent work stays coherent

This is the question underneath “how do we relate changes”, and it is a fair challenge: with no analysis meeting, two engineers can be working on adjacent things with nothing forcing them to notice each other.

Four mechanisms, none of which is a meeting.

Coordination without a coordination ritual
RiskWhat catches itWhen
Two people build the same thing The reuse stage. It reads a catalogue regenerated every commit, so work merged this morning is discoverable this afternoon. This is the mechanism doing most of the work here, and it is why the catalogue is generated rather than hand-maintained. Before either writes code
Two changes touch the same code Version control. It is a merge concern and it always was — an analysis meeting never actually prevented this, it just made people feel briefed. At merge
One change breaks another's assumptions Contract tests and breaking-change detection on the published interface. The machine says so at the moment it happens, which is considerably better than someone remembering a conversation from a fortnight ago. In CI, immediately
Two changes are individually fine and jointly wrong A person. Specifically the architecture forum, and the tech lead holding the system overview. Weekly — this is the one that genuinely needs the meeting
The honest cost of automating the breakdown

An analysis phase produced two things, and only one of them was task cards. The other was shared understanding — a team that decomposes a feature together ends up knowing that feature, including the parts they did not personally build.

Automating the decomposition gets you the cards without the side effect. That is a real loss and it should be named rather than waved past, because it shows up later as nobody being able to cover for anyone else.

Three things offset it, and they need to be deliberate rather than hoped for: reviewers come from the owning area, so people read work they did not write · approval requires writing a sentence about the change, which cannot be done without understanding it · and the architecture forum is genuinely collective, so the decisions that shape a feature are made by more than one person even when the implementation is not.

Watch for the symptom: one person is the only one who can answer questions about an area. That is the failure, and reviewer rotation is the cheapest fix.

One rule decides every gate: automate by reversibility, gate by irreversibility

A step runs unattended if undoing it is cheap, and needs a person if undoing it is expensive. That turns "how much do we trust the agent?" — which has no answer and gets settled by whoever is most senior — into "how good is our undo?", which is something you build and measure.

It also means gates disappear on their own merits as reversibility improves, rather than accumulating forever because removing one requires arguing for less caution.

The four risk lanes, since everything above refers to them

A lane is assigned automatically from the files a change touches, never from what the author claims about it. That is the whole mechanism — self-declared risk is always low.

How much process a change gets
LaneTypical changeWhat it gets
1 · CosmeticCopy, configuration, logging, documentation.Automated checks only. Ships on green, no human in the path — this is the lane that pays for the whole scheme.
2 · StandardOrdinary feature work.Automated checks, machine review, then one human reviewer.
3 · SensitiveAuthentication, personal data, anything with a database migration.All of the above plus a second reviewer, a security review, and an explicit rollback plan.
4 · ClinicalMember data, clinical logic.Everything in Lane 3 plus a named human approval before release. Rollback restores the system, not the person.
The rules need a team-size clause, stated now rather than discovered

Four rules elsewhere in this design are individually sensible and collectively impossible at eight engineers: one owning team per module, teams review their own code, Lane 3 needs two reviewers from the owning team, and reviewers rotate within the team. Split eight people across three surfaces and an owning team is two or three — so “two from the owning team” means everyone reviews everything, and rotation has nothing to rotate between.

Below roughly fifteen engineers: one reviewer from the owning area, and Lane 3’s second reviewer comes from anywhere in engineering. Rotation is an aspiration rather than a rule. Above fifteen, the rules apply as written.

This matters more than it looks, because a control that cannot be satisfied gets quietly ignored — and the habit of ignoring it survives the growth that made it satisfiable.

Where it runs

Two stages on a developer's machine, nine headless in CI. Specification and review are interactive because they need a conversation. Everything else runs on a trigger with nobody waiting, which is what makes it cheap and auditable.

The failure to design against is not overspending

The best-documented failure in this field is a company that measured a real productivity gain and cancelled anyway. Five thousand engineers lost the tooling despite that same company's study showing a 24% throughput improvement — because they piloted on flat-rate licensing, the real number arrived all at once, and nobody could defend it against a budget set before anyone knew what it would be.

They had the money. They lost the argument. So one named person owns the total monthly bill from the first month, and cost per merged change is the metric — because it is attributable and it trends.

Quote the cloud line separately

It is a shape, not a quote — nobody has modelled the workload, and it is the only figure here that could move by a factor of two. About two-thirds of the per-engineer number is indifferent to it. Say "roughly $150–250 per engineer for tooling and AI, plus hosting, which is load-dependent" — a single blended number invites a challenge on the part you can least defend.
